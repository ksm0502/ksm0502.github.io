# MORROW Troubleshooting

MORROW 프로젝트를 진행하면서 실제로 겪었던 문제와 해결 과정을 정리한 문서입니다.

단순히 오류 메시지를 나열하기보다, **문제 → 원인 → 해결 → 결과** 흐름으로 정리했습니다.

---

## 1. 장바구니 상태 관리 구조 개선

### 문제

프로젝트가 커지면서 상품 카드, 상품 상세 페이지, 장바구니 페이지, Header 등 여러 컴포넌트에서 동일한 장바구니 상태를 사용하게 되었습니다.

컴포넌트 간 상태 전달이 복잡해졌고, 새로고침하면 장바구니 상태가 초기화되는 문제도 있었습니다.

### 원인

여러 화면에서 공통으로 사용하는 상태를 지역 상태 중심으로 관리하면 Props 전달 범위가 커지고, 브라우저 새로고침 시 메모리에 있던 상태가 사라집니다.

### 해결

장바구니 상태를 Zustand Store로 분리했습니다.

`cartStore.js`에서 다음 기능을 전역 상태로 관리하도록 변경했습니다.

- 상품 추가
- 상품 삭제
- 수량 증가
- 수량 감소
- 장바구니 전체 삭제

또한 Zustand의 `persist` middleware를 적용해 장바구니 데이터를 `localStorage`에 저장하도록 구성했습니다.

### 결과

장바구니 관련 로직을 여러 컴포넌트에서 동일하게 사용할 수 있게 되었고, Header의 상품 개수와 Cart 페이지의 상태도 일관되게 유지되었습니다.

새로고침 이후에도 장바구니 데이터가 유지되도록 개선했습니다.

## 2. CSS 파일 비대화와 유지보수 문제

### 문제

기능과 페이지가 늘어나면서 하나의 CSS 파일에 Header, Hero, 상품 카드, 상품 상세, 장바구니, 인증, 반응형 스타일이 계속 추가되었습니다.

파일이 커지면서 특정 스타일의 위치를 찾기 어렵고, 수정 범위도 파악하기 어려워졌습니다.

### 원인

프로젝트 초반에는 하나의 CSS 파일로도 충분했지만, 페이지와 기능이 늘어난 이후에도 같은 구조를 유지한 것이 원인이었습니다.

### 해결

스타일을 역할별 파일로 분리했습니다.

```text
styles/
├── auth.css
├── cart.css
├── footer.css
├── global.css
├── header.css
├── home.css
├── notFound.css
├── product.css
├── responsive.css
└── wishlist.css
```

기본 레이아웃은 `global.css`, 기능별 스타일은 각각의 CSS 파일, 화면 크기에 따른 스타일은 `responsive.css`에서 관리하도록 역할을 나눴습니다.

### 결과

어떤 UI를 수정할 때 어느 파일을 확인해야 하는지가 명확해졌고, 스타일 수정 범위를 빠르게 파악할 수 있게 되었습니다.

프로젝트 규모가 커질수록 스타일의 역할 분리가 유지보수에 중요하다는 점을 경험했습니다.

## 3. Header 구조 변경 후 반응형 스타일 불일치

### 문제

PC 화면에서 Header의 좌우 정렬 기준이 main 콘텐츠와 맞지 않았습니다.

기존 Header는 화면 전체를 기준으로 좌우 padding을 적용하고 있었기 때문에 넓은 화면에서 MORROW 로고와 본문 콘텐츠의 시작선이 달랐습니다.

이를 해결하기 위해 Header 내부에 `.header-inner` wrapper를 추가했지만, 기존 `responsive.css`는 여전히 `header` 요소에 직접 flex 방향과 padding을 적용하고 있었습니다.

### 원인

Header의 DOM 구조는 변경했지만 반응형 CSS selector가 이전 구조를 기준으로 남아 있었기 때문입니다.

### 해결

Header의 역할을 두 부분으로 분리했습니다.

- `header`
  - sticky
  - 배경
  - border
  - backdrop filter
- `.header-inner`
  - `max-width: 1200px`
  - 중앙 정렬
  - flex layout
  - padding

그리고 태블릿 및 모바일 반응형 스타일도 `header`가 아니라 `.header-inner`를 대상으로 수정했습니다.

### 결과

PC에서는 Header와 main 콘텐츠의 좌우 기준선이 자연스럽게 맞았고, 모바일에서도 변경된 구조에 맞게 반응형 레이아웃이 정상적으로 동작하도록 정리했습니다.

이 과정을 통해 DOM 구조를 변경할 때 관련된 반응형 selector도 함께 점검해야 한다는 점을 확인했습니다.

## 4. 브라우저 콘솔 오류의 원인 분리

### 문제

개발 중 브라우저 콘솔에 애플리케이션 코드와 직접 관련이 없어 보이는 오류가 계속 표시되었습니다.

오류 메시지에는 `background.js`, 권한 관련 메시지, 403 응답 등이 포함되어 있어 React 프로젝트에서 발생한 문제인지 확인할 필요가 있었습니다.

### 원인 확인 과정

애플리케이션 코드만 보고 원인을 단정하지 않고 일반 브라우저 환경과 시크릿 모드에서 실행 결과를 비교했습니다.

시크릿 모드에서는 동일한 오류가 나타나지 않는 것을 확인했습니다.

### 해결

시크릿 모드에서 오류가 사라진 점을 바탕으로 프로젝트 코드보다 설치된 Chrome 확장 프로그램이 원인일 가능성이 높다고 판단했습니다.

애플리케이션의 실제 동작과 별개의 브라우저 확장 프로그램 오류로 구분해 프로젝트 코드에 불필요한 수정을 하지 않았습니다.

### 결과

콘솔 오류가 발생했을 때 메시지만 보고 애플리케이션 문제라고 단정하지 않고, 실행 환경과 외부 요소를 분리해 확인하는 방법을 경험했습니다.

## 추가 대응: SPA 배포 라우팅

아래 내용은 실제 오류가 발생한 뒤 수정한 사례가 아니라, Vercel 배포 전에 미리 대응한 내용입니다.

MORROW는 React Router의 `BrowserRouter`를 사용합니다.

SPA에서는 `/wishlist`, `/cart`, `/products/1`과 같은 주소를 직접 요청하거나 새로고침할 경우 배포 환경에 따라 404가 발생할 수 있습니다.

이를 방지하기 위해 프로젝트 루트에 `vercel.json`을 추가했습니다.

```json
{
  "rewrites": [
    {
      "source": "/(.*)",
      "destination": "/index.html"
    }
  ]
}
```

모든 경로를 `index.html`로 전달한 뒤 React Router가 클라이언트에서 실제 페이지를 처리하도록 구성했습니다.

이 항목은 실제 장애를 해결한 사례가 아니라, SPA 라우팅 구조를 확인하고 배포 전에 사전 대응한 사례입니다.
